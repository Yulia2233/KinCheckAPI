# KinCheckAPI v0.1.2 更新报告

## 版本目标

本版本把仿真结果从“包含播放器的网页目录”升级为 KinCheckAPI 自己导出的 `.kincheck` 数据包。数据格式与 Viewer 解耦，Agent 可以直接生成和读取，人可以使用独立 KinCheck Viewer App 查看同一份结果。

同时，本版本以 `examples/ex3` 和 `examples/ex4` 为装配体落地样例，把两个有真实几何结构的闭环机构从“零件模型”整理成 KinCheckAPI 可以读取的装配体数据：

```text
Part 定义
    -> Component 实例和初始姿态
    -> Connector 局部连接坐标
    -> Joint、Constraint、Closure
    -> Ground 和装配拓扑
    -> assembly.json、model.json、assembly.step、manifest.json
```

这两个示例的重点不是做一个好看的静态模型，而是验证 KinCheckAPI 能否保留真实机构的零件、连接关系、运动树和闭环边。

## ex3 和 ex4 装配体落地

### 1. ex3：经典曲柄摇杆四连杆

示例目录：

```text
examples/ex3/
```

#### 1.1 零件定义和实例

ex3 定义 7 个可复用 `Part`：

```text
part.ex3.base       固定机架
part.ex3.crank      输入曲柄
part.ex3.coupler    连杆
part.ex3.rocker     输出摇杆
part.ex3.pin        转轴销
part.ex3.bushing    铜套
part.ex3.spacer     间隔环
```

然后将这些 Part 实例化为 20 个 Component：

```text
4 个机构主体：base、crank、coupler、rocker
4 个转轴销
8 个铜套
4 个间隔环
```

重复使用的销、铜套和间隔环仍然只有一个 Part 定义，但在每个转轴位置创建独立 Component。这样既保留真实的 CAD 装配结构，也不会把重复硬件错误地当成同一个零件实例。

#### 1.2 几何尺寸和初始姿态

ex3 在 `dimensions.py` 中集中定义机构尺寸：

```text
Ground frame  120 mm
Crank          35 mm
Coupler       110 mm
Rocker          80 mm
初始曲柄角     55 degrees
```

`initial_pose()` 先固定左右两个机架转轴，再根据曲柄角计算曲柄销位置，最后通过圆交点求出连杆和摇杆的公共转轴。两个圆交点代表两个装配分支，示例明确选择上方分支，确保初始几何姿态闭合。

每个运动主体都以计算得到的节点位置和连杆方向放置，不能只用一个默认原点姿态代替。

#### 1.3 Connector 和运动关系

四个运动主体通过明确的 Connector 连接：

```text
Base    conn.pivot.left   <-> Crank   conn.input
Crank   conn.output       <-> Coupler conn.input
Base    conn.pivot.right  <-> Rocker  conn.ground
Coupler conn.output       <-> Rocker  conn.output
```

四个关系都是转动连接，但其中前三条组成运动树，最后一条是闭环边：

```text
树边：
    joint.ex3.ground_crank
    joint.ex3.crank_coupler
    joint.ex3.ground_rocker

闭环边：
    joint.ex3.coupler_rocker
    closure.ex3.coupler_rocker
```

对应的运动树为：

```text
Base (Ground)
├── ground_crank -> Crank
│   └── crank_coupler -> Coupler
└── ground_rocker -> Rocker

Closure:
    Coupler -> Rocker
```

闭环边必须同时记录在装配关系和显式 `closures` 数据中，不能因为运动树只能有一个父节点就丢弃。

#### 1.4 硬件固定关系

销、铜套和间隔环通过固定约束安装到对应机构主体：

```text
Pin      -> 所属转轴主体
Bushing  -> Base、Crank、Coupler 或 Rocker
Spacer   -> Base、Crank 或 Rocker
```

这些固定关系用于表达真实产品结构，不能被视为新的运动自由度。它们在完整 CAD 装配体中存在，但在运动学树中属于辅助刚性附件。

### 2. ex4：Theo Jansen 多闭环腿机构

示例目录：

```text
examples/ex4/
```

#### 2.1 零件定义和实例

ex4 定义 12 个可复用 `Part`：

```text
frame
drive_crank
upper_coupler
upper_triangle
lower_rocker
lower_coupler
trailing_link
foot_triangle
foot
pin
bushing
spacer
```

其中前 9 个是运动主体，后 3 个是重复使用的装配硬件。

最终装配体包含：

```text
9 个运动主体
8 个关键节点 × 3 个硬件实例
= 33 个 Component
```

每个三角形构件作为一个刚性 Part 建模，而不是拆成几根独立连杆。这样 `upper_triangle` 和 `foot_triangle` 的内部几何关系由 Part 本身保证，不会在装配拓扑中制造多余自由度。

#### 2.2 几何尺寸和初始姿态

`assembly.py` 中的 `calculate_design_pose()` 根据经典 Jansen 比例计算一组真实闭合姿态：

```text
1. 固定 frame 的左右两个转轴
2. 按 120.3 degrees 计算输入曲柄端点
3. 用圆交点求 upper_node
4. 根据 upper_triangle 的刚性尺寸求 rear_node
5. 用圆交点求 lower_node
6. 用圆交点求 foot_rear
7. 根据 foot_triangle 的尺寸求 foot_tip
```

计算得到的节点位置用于放置每一个运动主体，计算得到的方向用于设置每个 Component 的初始姿态。上方节点和下方节点明确选择指定的圆交点分支，保证得到的是同一套机构姿态。

#### 2.3 运动树

ex4 从 `frame` 出发建立一棵主运动树：

```text
Frame (Ground)
├── frame_to_crank -> Drive Crank
│   └── crank_to_upper_coupler -> Upper Coupler
│       └── upper_coupler_to_upper_triangle -> Upper Triangle
│           └── upper_triangle_to_trailing -> Trailing Link
│               └── trailing_to_foot_triangle -> Foot Triangle
│                   └── foot_triangle_to_foot -> Foot
└── frame_to_lower_rocker -> Lower Rocker
    └── lower_rocker_to_lower_coupler -> Lower Coupler
```

树边共 8 条：

```text
frame -> crank
crank -> upper_coupler
upper_coupler -> upper_triangle
frame -> lower_rocker
lower_rocker -> lower_coupler
upper_triangle -> trailing
trailing -> foot_triangle
foot_triangle -> foot
```

`foot_triangle_to_foot` 是固定关系，但为了表达脚垫属于运动链，它也保留在树结构中。

#### 2.4 三条闭环边

ex4 额外保存三条闭环边：

```text
upper_triangle -> frame
lower_coupler  -> crank
foot_triangle  -> lower_rocker
```

对应的 ID 为：

```text
joint.jansen.closure.upper_triangle_to_frame
joint.jansen.closure.lower_coupler_to_crank
joint.jansen.closure.foot_triangle_to_lower_rocker
```

它们构成三个相互共享零件和关节的闭环：

```text
上部闭环：
    Frame -> Crank -> Upper Coupler -> Upper Triangle -> Frame

下部驱动闭环：
    Frame -> Crank -> Lower Coupler -> Lower Rocker -> Frame

脚部闭环：
    Lower Rocker -> Upper Triangle -> Trailing Link
        -> Foot Triangle -> Lower Rocker
```

ex4 的关键不是把三个环分别复制成三个独立机构，而是在一套共享 Component 图中保存 8 条树边和 3 条闭环边。后续求解器必须能识别这些关系属于同一个多闭环装配体。

#### 2.5 硬件固定关系

ex4 在以下 8 个节点放置销、铜套和间隔环：

```text
left_frame
drive_frame
crank_node
upper_node
rear_node
lower_node
foot_rear
foot_tip
```

每个节点有：

```text
Pin      -> 节点所属主体
Bushing  -> Pin
Spacer   -> Pin
```

这些关系把硬件接入完整产品图，但不改变机构的主要运动自由度，也不能被当成额外的闭环。

### 3. 两个示例共同的装配流程

ex3 和 ex4 都按照以下顺序完成从几何模型到装配体的转换：

```text
1. 定义可复用 Part 和几何形状
2. 在 Part 上定义 Connector 局部坐标
3. 根据机构尺寸计算一套初始闭合姿态
4. 创建 Component 实例并写入初始 Placement
5. 指定 Ground
6. 添加主要 Joint
7. 区分 tree edges 和 closure edges
8. 把 Closure 写入显式闭环记录
9. 添加销、铜套、间隔环等固定硬件
10. 检查关系、节点重合和初始几何闭合
11. 导出装配体和全部 Part 资产
12. 生成并校验 manifest
```

装配体中需要同时保留两种结构：

```text
完整 CAD 装配图：
    所有 Component、硬件和固定关系

运动学拓扑图：
    主要运动主体、树边和闭环边
```

不能用运动树替代完整 CAD 装配图，也不能用完整硬件图直接当作运动树。

### 4. 生成的装配体文件

两个示例都必须生成相同结构的 artifact：

```text
artifact/
    model.json
    assembly.step
    assembly.json
    manifest.json
    parts/
        <part_id>.part.json
        <part_id>.step
        <part_id>.stl
```

其中：

- `model.json` 保存可重放的 CAD 建模图；
- `assembly.step` 保存完整装配几何；
- `assembly.json` 保存 Part、Component、Connector、Joint、Constraint、Ground、KinematicTree 和 Closure；
- `manifest.json` 保存所有输出文件的相对路径、大小和 SHA-256；
- `parts/` 保存每个唯一 Part 的 JSON、STEP 和 STL 资产。

`assembly.json` 不能只保存零件名称和静态位置，至少要明确保存：

```text
assembly_id
part definitions
component instances
component initial placements
connector references
joints and constraints
ground component
tree edge IDs
closure edge IDs
parent_component_id
closure records
```

### 5. 当前范围

ex3 和 ex4 在本版本中完成的是：

- 真实几何 Part 定义；
- 可复用 Part 实例化；
- Component 初始姿态；
- Connector 连接坐标；
- Ground；
- Joint 和固定硬件关系；
- 运动树；
- 闭环边和 Closure 数据；
- 完整 artifact 和 manifest。

本版本不宣称已经完成：

- ex3 的整段闭环运动求解；
- ex4 的整段多闭环运动求解；
- 闭环机构的动力学；
- 接触、摩擦和强度分析。

后续运动求解器必须消费这里保存的树边和 Closure，而不能根据零件名称重新猜测闭环结构。

## 新增公开 API

```python
from kincheckapi import export

artifact = export.motion_package(
    assembly=assembly,
    motion_result=motion_result,
    output_path="ex2.kincheck",
    asset_root=artifact_root,
)

check = export.validate_package(path=artifact.path)
package = export.read_package(path=artifact.path)
```

- `export.motion_package()`：生成确定性的 `.kincheck` 文件。
- `export.export_motion_package()`：同一导出函数的明确别名。
- `export.validate_package()`：返回结构化格式、哈希、路径、引用和 schema 校验结果。
- `export.read_package()`：严格校验后重建 `AssemblyModel` 和 `MotionResult`。
- `MotionPackage.read_mesh()`：按 Part ID 读取校验后的 STL 数据。
- 新增 `MotionPackageArtifact`、`MotionPackage` 和 `MotionPackageError`。

姿态计算集中到新的 `kincheckapi.pose` 公共模块：

```python
from kincheckapi.pose import (
    compose_pose,
    inverse_pose,
    orientation_error_rad,
    relative_pose,
    rotate_vector,
    transform_point,
)
```

- `rotate_vector()`：旋转向量。
- `transform_point()`：变换空间点。
- `compose_pose()`：合成父级和子级姿态。
- `inverse_pose()`：计算反向姿态。
- `relative_pose()`：计算子级相对父级的局部姿态。
- `orientation_error_rad()`：计算两个朝向的最短夹角。
- 内置物理后端 后端统一调用公共姿态函数，删除重复的私有姿态合成和局部姿态实现。
- 已支持的齿轮/皮带约束会记录连接点位置和轴线方向残差；传动耦合保留标量方程残差，方向残差按无几何端点处理。

## 格式特性

- ZIP 容器内只保存 JSON 数据和 STL 网格，不嵌入网页代码或 内置物理后端 对象。
- `manifest.json` 记录 schema、单位、成员大小、SHA256、Part/网格映射和缺失网格。
- 装配快照、运动轨迹和验证摘要分开保存，Viewer 可以只读取需要的部分。
- 相同网格按 SHA256 去重，重复 Part 不重复占用文件空间。
- 导出使用固定 ZIP 时间和排序，输入相同则输出字节级一致，适合缓存和结果比较。
- `Pose` 构造时会将有限且非零的 `orientation_xyzw` 自动归一化为单位四元数；不同数值尺度但表示同一旋转的输入会得到一致姿态，零四元数和非有限值继续被拒绝。
- 读取器拒绝路径穿越、重复成员、未索引文件、大小/哈希篡改和不支持版本。

## 独立 KinCheck Viewer

Viewer 位于仓库顶层 `viewer/`，不在 `src/kincheckapi` 中，也不进入 KinCheckAPI wheel。它只消费 `.kincheck` 文件，不调用运动学求解器。

```bash
python viewer/kincheck_viewer.py package_output/ex1.kincheck --serve
```

解包器检查 manifest、成员路径、大小和 SHA256，然后提取 STL、转换组件轨迹并启动 `http://127.0.0.1:8767/`。播放器支持播放/暂停、时间轴、倍速、视角控制和组件显示。`--input-joint`、`--output-joint`、`--expected-ratio` 只是可选的传动比指标展示参数，不参与仿真记录和回放。

现有 `visualization.export_motion_viewer()` 仅作为旧网页导出兼容入口保留；它不是 `.kincheck` 格式的一部分，也不是新的解包入口。

## 组件世界姿态结果范围

本次补充了 `ComponentResultScope`，用于明确 `MotionResult.trajectories` 中组件世界姿态的输出范围：

```python
scenario = scenario.set_component_result_scope(
    scenario=scenario,
    scope="all",
)
motion = kinematics.solve_motion(scenario=scenario)
```

范围含义：

- `requested`：保持原有行为。没有指定组件请求时记录全部组件；指定了组件请求时只记录被请求组件。
- `all`：忽略组件请求列表，记录装配体中每个 Component 的世界姿态轨迹，包括 fixed 刚性组里的销、铜套、垫片等辅助零件。

内置物理后端 在两种模式下都会计算完整模型的运动。区别只在于后端采样并写入 `MotionResult` 的组件集合。结果元数据现在记录 `component_result_scope`，`.kincheck` manifest 和 Viewer manifest 也会保留这一标记。

推荐用途：

- 普通关节和传动分析使用 `requested`，减少结果体积。
- 整机 Viewer、离线碰撞检查和完整 CAD 结果导出使用 `all`，避免未记录的固定件被回放为初始姿态。

该功能新增 10 个测试用例，覆盖默认兼容、不可变设置、非法范围、场景 JSON 往返、requested 过滤、ex3/ex4 全组件轨迹、世界姿态采样、请求覆盖和 `.kincheck` 往返。
